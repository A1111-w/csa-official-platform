# CSA Project Instructions

## Read Before Editing

- Read `README.md`, `docs/project-status.md`, `docs/development-constraints.md`,
  `CHANGELOG.md`, and `.specify/memory/constitution.md` before changing this project.
- Inspect actual source and configuration before editing documentation. Distinguish
  implemented behavior, plans, historical evidence, and unverified assumptions.
- Application code lives in `csa-official-backend/` and
  `csa-official-frontend/`. This is not an empty Spec Kit scaffold.
- `AGENTS.md` is the canonical agent entry point. `agent.md` only links here;
  do not maintain a second, conflicting rule set.

## Git Isolation

- This project owns a standalone `.git` directory. Keep its history, index,
  branches, configuration, and remotes separate from every other project.
- Before Git mutations, verify `--show-toplevel` and `--absolute-git-dir` resolve
  to this project and its own `.git` directory. Stop if they point elsewhere.
- Use `git -C "<verified-project-root>" ...` for all Git commands. Do not rely on
  a terminal's previous working directory.
- Do not change global Git configuration or persist a guessed author identity.
- Do not initialize, stage, commit, or modify files in sibling or parent projects.
- Stage explicit project paths and inspect the staged diff before committing.
  Never include credentials, environment secrets, or agent session data.
- Preserve existing user changes. Do not reset, clean, overwrite history, or
  force-push without an explicit request.
- Keep `main` as the baseline. Use `codex/` for manually created work branches;
  respect branch conventions generated by the project's Spec Kit workflow.
- Do not add or alter remotes, or push commits, unless the user requests it.
- The original CSA worktree is retained outside this directory for rollback only.
  It is not the working copy for this task. Never edit or commit there.
- `.migration-backup/` is private local migration evidence. Never stage it,
  its nested Git repository, or its history bundle.

## Required Feature Delivery

- Every agent MUST update affected documentation and append a feature-specific
  Markdown record before declaring a feature complete. This includes fixes,
  refactors, configuration changes, documentation changes, and delegated work.
- Use the checklist and documentation impact table in
  `docs/development-constraints.md`. Update actual behavior documentation, not
  just `CHANGELOG.md`; for documentation-only work, update the relevant document.
- Add a unique entry to `CHANGELOG.md` using
  `docs/templates/change-record.md`. Include author/agent, date, related task,
  scope, affected paths, verification commands and actual results, risks,
  remaining work, and rollback approach.
- Keep each feature's implementation, tests, documentation, and record in the
  same delivery. Do not defer documentation to a later conversation or to the
  final phase of an unrelated feature.
- Do not mark required tasks complete if documentation, a record, or required
  verification is missing. Report partial completion or a blocker explicitly.
- For delegated work, assign non-overlapping files. The delegated agent supplies
  its documentation and record; the coordinating agent integrates shared-file
  edits and checks evidence before accepting the feature.
- Completion messages must identify changed behavior, updated docs, record ID,
  test outcomes, and unresolved limitations. Historical test counts are not
  evidence that the current working tree passed.

## Implementation Boundaries

- This branch uses Spring Boot/Java and Vue 3/TypeScript, as explicitly requested
  by the user on 2026-11-08. React/Next.js remains on `codex/agent-rag-evaluation`.
  Read `pom.xml` and `package.json` for actual versions; avoid incidental upgrades.
- Keep browser authentication in HttpOnly cookies, backend authorization, CSRF,
  account/session-version checks, and file ownership checks intact.
- Do not reconnect tests to production services or copy secrets into examples.
  Use isolated fixtures and the backend test profile for automated validation.
- Database changes require new Flyway migrations. Do not rewrite applied
  migrations, import seed data into production, or run recovery scripts as setup.
- Use the npm lockfile consistently; do not add a second package manager.
- Run risk-appropriate tests and `tools/check-study-guide-drift.ps1` when relevant.
  Record skipped checks with reasons; do not claim CI or deployment passed
  merely because source or configuration files exist.

## Spec Kit

- The shared CLI is installed outside the repository. Run project commands from
  this repository root.
- Keep `.specify/` and `.agents/skills/speckit-*` under version control.
- Use the project-local Spec Kit skills for requirements, planning, tasks, and
  implementation. Do not copy them into the user's global skills directory.
- Follow the project constitution for documentation and delivery gates. Include
  those gates in each feature's plan and tasks; do not rewrite bundled templates
  or generated skills to encode project rules.
- Verify `specify integration status` after integration changes.
